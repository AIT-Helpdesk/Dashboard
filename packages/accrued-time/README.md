# @dashboard/accrued-time

Lives in the new admin-only **Builders** category (`nav-layout.json`, `hidden: true` on the category itself, plus `dashboardPage.restrictedTo: ["amber@ambientit.com.au"]` on both this page and `@dashboard/times` -- neither the category nor either page's client.js/server.js/API is reachable by anyone but the one dashboard-admin account, same "checked in three places, 404 not 403" mechanism `@dashboard/registry.js` already documents for every `restrictedTo` page).

Page `<h1>` reads **"Accrued Time Checker"**, by request (the package/directory id, route (`/api/accrued-time`), and sidebar label all stayed `accrued-time`/"Accrued Time" -- only the on-page heading changed, same "rename the display, not the plumbing" convention `@dashboard/times` already established for its own "Time Summaries" rename).

By request: "selectors for date from and to, Resource Name, & Ticket Number. Then select data from Autotask. Use the date to select time entries in that period. Use Resource and Ticket to narrow down the selection." Two lists (Complete, then Not Complete, see below), each one row per ticket ordered by Ticket Number: Ticket #, Ticket Title, Ticket Status, then a real-hours sum for each of five Work Type buckets.

- `client.js` -- frontend module. Exports `id`, `label`, `mount(container)`.
- `server.js` -- Express router mounted by the shell at `/api/accrued-time`. Read-only.

## Filters

- **From / To** -- required, same date-range convention (and quick-set buttons -- Today/Yesterday, This Week/Last Week, This Month/Last Month, paired and stacked, small light-pill style, same AEST-anchored math, same "highlight whichever button produced the current dates, cleared on hand-edit" behaviour) as `@dashboard/times`, by request ("change the buttons on the Accrued Time page to be like the Time Summaries buttons"; "highlight the chosen button until the dates are manually editted (both pages)"). Defaults to today (was last week, Mon-Sun, by request).
- **Resource** -- optional `<select>`, populated from `GET /api/accrued-time/resources` (active, non-API-user resources -- `Resources.licenseType 7`, same real fact confirmed in `@dashboard/times`' own README). "All Resources" (blank) by default; narrows the `TimeEntries` query to `resourceID eq <id>` when picked.
- **Ticket #** -- optional text input, exact match against the real `Tickets.ticketNumber` field (the human-readable "T20260101.0001"-style value, resolved to the ticket's own internal id first, then used to scope the `TimeEntries` query to `ticketID eq <id>`). A value that matches no real ticket returns `{ completeRows: [], ticketNumberNotFound: true }` from the main route (`{ otherRows: [], ticketNumberNotFound: true }` from the on-demand `/incomplete` route, see "Two lists" below) rather than silently falling back to "every ticket in the date range" -- the client shows an explicit "No ticket found with number ..." message for this case.
- **Show Issues Only** -- checkbox, by request placed right after the Load button (originally its own row above the date range, moved by request). A pure client-side display filter (`client.js`, no separate fetch) -- when checked, both lists are filtered down to only rows carrying EITHER kind of issue (see "END vs ING" below), `hasIssue(r)` being the exact same union both row-shading rules themselves use, so "checked" and "shaded red or yellow" can never disagree. Applies to whichever of the two lists is currently in hand -- Complete always; Not Complete only once it's actually been fetched (see "Two lists" below).

## Data selection -- the date range picks TICKETS, not entries

**The date range decides which tickets qualify to appear at all -- it does NOT clip any column's own total.** Two real fetches, `server.js`:

1. **Qualification**: ticket-linked `TimeEntries` (`exist ticketID`) with `dateWorked` in the selected range (Resource/Ticket # filters apply here too) -- a ticket qualifies if at least one of ITS OWN entries in that window has a real Work Type NAME starting with `"Accrue-"` (single hyphen, so it also catches any real work type beyond the 4 named ones below, e.g. a hypothetical future `Accrue-Something`). **A real bug caught by the user's own question** ("are you only showing tickets that HAVE at least one time entry work type starting with Accrue-?") -- the first version wasn't: it showed every ticket with ANY ticket-linked time in the period, Accrue-related or not. Confirmed the hard way against real data: 259 of 304 rows for one real test week had ZERO Accrue-* time and shouldn't have been there at all -- only 45 real tickets actually had any.
2. **Totals**: once a ticket qualifies, ALL FIVE columns sum that ticket's ENTIRE real history (`fetchByFieldIn(client.timeEntries, 'ticketID', ticketIds)`, no date filter at all) -- not just the entries that happen to fall inside the selected window. **A second real bug, caught by the user directly**: "The Accrue--ING values aren't right. Example. Ticket T20260729.0029." Investigated against real data: that ticket's real `Accrue--ING` work happened weeks (`2026-07-30` through `2026-08-03`) before the real `Accrue--END`/`Accrue--END-No Bill` work that closed it out (`2026-08-31`) -- so the ORIGINAL date-scoped-totals design showed `Accrue--ING` as `2.68h`, `0.45h`, or `0h` for that exact same real ticket depending only on which date range happened to be picked, none of them "wrong" in isolation, just an artifact of an arbitrary window clipping a ticket's real total -- which also broke the whole point of the END-vs-ING reconciliation shading below (a ticket can look "mismatched" purely because the chosen window didn't happen to span its whole real history). Confirmed with the user directly that the fix is "yes -- full all-time totals per ticket, using the date range only to decide which tickets qualify." Re-verified against real data after the fix: three different date ranges that each independently qualify the same real ticket (T20260729.0029) now all agree on the exact same totals (`2.6835` / `0.0167` / `0.0167`), and a different real ticket (T20260518.0013) that previously showed `Accrue--ING: 0` for one real week (its real ING work fell outside that window) now correctly shows its real all-time total, `7.80h`.

## Ticket # and Ticket Title columns

`Tickets.ticketNumber` (linked, same real popup-window `window.open(url, '_blank', 'noopener,noreferrer,width=1200,height=900')` convention every ticket link on this dashboard uses) followed by `Tickets.title`, by request ("add ticket title after Ticket #").

## Two lists -- Complete, then Not Complete

By request ("1st list for Complete tickets (include Billing - Contract) and the second list for all others"). Split server-side, `COMPLETE_STATUS_LABELS` -- the exact same real "Complete" bucket `@dashboard/times`' own Accrue--ING-by-Status table already uses (`Complete` id 5, `Billing - Contract` id 20, confirmed real in that page's own README), reused verbatim rather than re-derived. Each list independently sorted by Ticket Number. Confirmed against real data: 30 real Complete + 15 real Not Complete = 45, no status leaking across lists either way.

**"Other" renamed to "Not Complete"**, by request, and its own data is NOT fetched as part of the main load at all -- "for the second table, don't retrieve the data initially ... add a button for Show Incomplete Tickets", same "don't retrieve it by default so the page is faster" reasoning `@dashboard/times`' own Work-Type Reconciliation section already established:

- `resolveTicketSplit()` (`server.js`) does the (cheap) qualifying-ticket-and-status-split work ONCE, shared logic behind both routes below, but stops there -- it does NOT fetch either list's own all-time `TimeEntries` history (the expensive part, `buildRows()`).
- `GET /api/accrued-time` (main route, fired on Load) calls `buildRows()` for the Complete ticket ids ONLY -- the Not Complete ticket ids are known (from the split) but their own rows are never built, so their all-time history is never fetched at all unless asked for.
- `GET /api/accrued-time/incomplete` (new, on demand) independently re-derives the same split (same "each on-demand route re-derives its own scope rather than sharing it across separate HTTP requests" convention `@dashboard/times`' own `/work-type` route already established) and calls `buildRows()` for the Not Complete ticket ids.
- **Show Incomplete Tickets** button, by request, sits next to (not inside) the Not Complete heading -- fires the `/incomplete` request the FIRST time it's clicked; the fetched rows are cached client-side (`lastIncompleteData`), so a further click just toggles the table's own visibility, no re-fetch, which is what the button's own label change to **Hide Them** (rather than, say, "Reload") signals. New Load params reset the cache (`lastIncompleteData = null`), so the next click re-fetches for the new params rather than showing stale data.
- The Not Complete section's own heading only ever comes from `listHtml()`'s own generated `<h2>` (which includes the row count) once the table is actually shown -- an earlier version also had a second, static "Not Complete" heading sitting next to the button itself, which just duplicated it once the table appeared; removed by request ("the heading for them appears twice ... Get rid of the one before the button").

Confirmed against real data: the main route's own JSON response now has no `otherRows` key at all (`{ from, to, completeRows }`); the `/incomplete` route independently returns the real Not Complete rows (15 of them for one real test week), and Complete (30) + Not Complete (15) still sums to the same real 45-ticket total confirmed before this split existed.

## The five Work Type buckets

**"Work Type" is `TimeEntries.billingCodeID`**, same field `@dashboard/times`' own Work-Type Reconciliation section uses. **Resolved via the real `BillingCodes` entity** (`client.billingCodes`, `fetchByFieldIn(..., 'id', ...)`, `.name`) -- confirmed the hard way during a real diagnostic run against this exact route: an earlier version tried `getPicklistLabels(client.timeEntries, 'billingCodeID')` (the mechanism that correctly resolves `Tickets.status` below) and got back unresolved `"Work Type #29682804"`-style labels for every real entry, because `billingCodeID` is a reference to a real `BillingCodes` record (a real Autotask internal id, not a small-integer picklist value) -- `getPicklistLabels()` reads Autotask's `entityInformation/fields` picklist metadata, which has nothing for a reference field like this. Fixed to match `@dashboard/times`' own already-proven `fetchWorkTypeBreakdown()` resolution exactly; a hand-verified diagnostic re-run against a real ticket's own raw `TimeEntries` confirmed every bucket sum matches exactly once fixed.

Four named buckets, real confirmed exact strings (same tenant, same field, cross-checked against `@dashboard/times`' own README "Confirmed against real data" section -- the request's own "Accrue--END-No-Bill" is normalized to the real confirmed spelling, "Accrue--END-No Bill", a space not a hyphen before "Bill", same "request spelling -> real confirmed spelling" convention that page's own `WORK_TYPE_FIXED_LIST` already established):

1. `Accrue--ING` -- header unchanged. Plain `hoursWorked`, no offset adjustment -- see "Offset Hours" below for why.
2. `Accrue--END` -- **header shortened to "END"**, by request. Column (header + body cells) very lightly shaded green (`.accrued-time-end-col`, `color-mix(in srgb, #16a34a 8%, transparent)` -- the same #16a34a this dashboard already uses for header shading elsewhere, just much lower opacity than the usual 18-20%, to read as a light tint grouping this column with the next one, not a strong highlight). A vertical divider sits on its LEFT edge, by request ("put vertical lines on the table before column END and after column NO BILL") -- `styles.css`, `:nth-child(6)` (bumped from `:nth-child(5)` when the Client column, below, shifted every column after it over by one). **Summed as `hoursWorked + offsetHours`**, not just `hoursWorked` -- see "Offset Hours" below.
3. `Accrue--END-No Bill` -- **header shortened to "NO Bill"**, by request. Same light green shading as END, for the same "these two columns are related" reason. A vertical divider sits on its RIGHT edge (`:nth-child(7)`, same column-shift note as END above), bracketing the END/NO Bill pair together. Same `hoursWorked + offsetHours` sum as END, see "Offset Hours" below.
4. `.Standard Support` -- **header shortened to ".STD"**, by request. Same `hoursWorked + offsetHours` sum as END/NO Bill -- see "Offset Hours" below.
5. **Other** -- every other real Work Type found on that ticket's own time entries in the period (confirmed real examples: Administration, Maintenance, Onsite  Support, Quoted Labour Hours, Travel - under 50Kms, REWORK, Tools/Rollouts, Sales, Emergency), summed together (each entry's own `hoursWorked + offsetHours`, same adjustment as .STD/END/NO Bill -- see "Offset Hours" below). **Hovering any non-zero Other cell shows a tooltip** (`title` attribute) listing the distinct real Work Type names that contributed to it for that specific ticket, by request -- computed PER TICKET, not globally, since two different tickets' own "Other" mixes can differ.

## Offset Hours -- folded into END, NO Bill, .STD, and Other

By request: "Accrue--END and --END-NO BILL often have a time offset. please add the time offset when summing the time." Confirmed against real data before touching the code: `TimeEntries.offsetHours` is a real field (also shown as its own column in `@dashboard/times`' own time-entry drill-down), and real Accrue--END/Accrue--END-No Bill entries very commonly carry a substantial nonzero value in it -- 25 of 28 real END/No-Bill entries for one real week had one (real examples: `1.4833`, `1.1667`, `2`), each logged alongside a near-zero `hoursWorked` (`~0.0167h`, a one-minute "closing click") -- the real accrued time sits in `offsetHours`, not `hoursWorked`, for these two work types. Confirmed `Accrue--ING` never does this (0 of 49 real ING entries the same week had any nonzero `offsetHours`), so ING is deliberately left out of this adjustment, still plain `hoursWorked`.

**Widened to `.Standard Support` and `Other` too**, by a follow-up request ("in END and NO BILL hours we adjust by the offset. can you please adjust up or down by any offset entered for .STD and OTHER as well") -- `adjustedHours` (`hoursWorked + offsetHours` per entry, `server.js`) is now applied to all four of `bucket.accrueEnd`/`bucket.accrueEndNoBill`/`bucket.standardSupport`/`bucket.other`, only `bucket.accrueIng` still sums plain `hoursWorked`. "Up or down" is deliberate wording -- `offsetHours` can be negative as well as positive, and this is a plain add (`hours + (e.offsetHours || 0)`), not floored at zero, so a real negative offset genuinely reduces a bucket's total rather than being clamped away.

Re-verified against real data after the original END/NO Bill fix: ticket T20260729.0029's own `Accrue--END` went from `0.0167h` to the real `1.5h` (`0.0167 + 1.4833`), and `Accrue--END-No Bill` from `0.0167h` to `1.1834h` (`0.0167 + 1.1667`) -- exact hand-matches. The knock-on effect on the whole red/yellow split (below) is real, not incidental: END totals were being massively undercounted before this fix, which is very likely what "the Accrue--ING values aren't right" (the report that led to the all-time-totals fix above) was actually seeing -- END looking implausibly small next to ING for tickets with real offset time.

## END vs ING -- whole row shaded red or yellow

Rules replaced twice by request, now settled on a simple directional comparison: "our rules for shading rows red ... If the sum of --END times is less than --ING time - RED; If greater - Yellow." `endTotal(r)` is `accrueEnd + accrueEndNoBill`; `isRed(r)` is `endTotal(r) < accrueIng`, `isYellow(r)` is `endTotal(r) > accrueIng` (`client.js`) -- a row is red XOR yellow XOR neither, never both (the two conditions are mutually exclusive by construction), so this single, simpler rule cleanly subsumes the earlier "END with no ING at all" case too: any real END > 0 with ING = 0 trivially satisfies `endTotal(r) > accrueIng`, so that case is just yellow now, no separate check needed.

**5-minute allowed variance**, by request, added just after the rule first shipped as an exact comparison: `VARIANCE_HOURS = 5 / 60`. `isRed(r)` is `endTotal(r) < accrueIng - VARIANCE_HOURS`; `isYellow(r)` is `endTotal(r) > accrueIng + VARIANCE_HOURS` -- END within 5 minutes of ING either side now stays uncoloured, a tighter window than the original (since-replaced) 15-minute mismatch tolerance.

`.accrued-time-red-row` -- same #dc2626 red this dashboard already uses for every other mismatch/reconciliation warning, 12% opacity. `.accrued-time-yellow-row` -- by request ("a little bit lighter but more yellowy"), `#facc15` (a purer, less amber/gold yellow than this dashboard's own usual #eab308 warning colour -- `.wsp-dot--coming`/`.text-highlight-yellow`) at 9% opacity, lighter than the red row's 12%. Both shade the WHOLE row (all cells, including the two green-shaded END/NO Bill cells -- a more specific selector wins there, see `styles.css`'s own comment).

"Show Issues Only" (above) catches both colours -- `hasIssue(r)` is `isRed(r) || isYellow(r)`, the union. **Numbers below are from before the all-time-totals fix and the 5-minute variance** (see "Data selection" above and "Confirmed against real data" below for the current, correct picture) -- kept here as a record of what was checked at each step rather than re-verified per rule change: under the exact-comparison version of this rule, one real week's 45-ticket set (see "Confirmed against real data" for how that number itself later changed) split 32 red / 12 yellow / 1 clean, including a real row with `accrueIng` exactly `0.25` against an `endTotal` of exactly `0.25`, correctly uncoloured even before the variance existed.

**"- N Mismatches" next to the Complete heading**, by request ("next to COMPLETE (Count) please add - Count with Mismatch ... only if there are RED lines and show only the count of REDs not Yellows. make the text for the Count with Mismatch red") -- `mismatchCountHtml()` (`client.js`), RED rows only (`isRed(r)`, never `isYellow(r)`), only rendered at all when the count is above zero (a real "- 0 Mismatches" reading would just be noise next to "Complete (N)"), red text (`.accrued-time-mismatch-count`, same #dc2626 as everywhere else on this page). Scoped to the Complete list only (`listHtml()`'s new `opts.showMismatchCount`), by request -- Not Complete doesn't get one. Confirmed against real data: one real week's Complete list (30 tickets) had 9 real red rows and 4 real yellow ones -- the heading's own count only ever reflects the 9, never the 4.

**"- HH:MM" next to the same heading, right after the Mismatch count**, by request ("add at the top next to complete and mismatch the actual sum of time of the difference between --ING and (--END*)"), which went through several follow-up corrections: first narrowed to only `END* > ING` (yellow) rows, then corrected to the opposite ("I only want the difference of the sums of the mismatch lines where the ENDs are smaller than the --INGs"), then stripped of its own descriptive label entirely ("remove all the descriptive text for that calculation and just show the hours as HH:MM after MISMATCHES") -- `diffSumHtml()` (`client.js`) sums `accrueIng - endTotal(r)` ONLY across rows where `isRed(r)` is true, the exact same variance-aware definition both the row shading AND the "- N Mismatches" count above already use ("the mismatch lines" confirmed this is meant to be the SAME rows that count reports on, just summed instead of counted). Rows where END* is bigger (yellow) or within the 5-minute variance (uncoloured) don't contribute to the sum at all, not even as a zero. Every qualifying row's own difference is positive by construction (END* smaller than ING), so the total is always `>= 0`. Formatted HH:MM (`formatHms()`, same rounding/rollover convention `@dashboard/times`' own `formatHms()` uses), not `X.XXh` -- no label at all now, just a leading `- ` (not itself descriptive text -- the same separator the mismatch count's own span already uses). Plain muted text (`.accrued-time-diff-sum`), not alarm red. Scoped to the Complete list only (`opts.showDiffSum`), matching the mismatch count's own scope.

## Confirmed against real data

**Current state, all fixes combined** -- one real week (31 Aug - 6 Sep 2026), no filters: **45 real tickets qualify** (30 Complete + 15 Not Complete, unchanged by either the all-time-totals or offsetHours fix -- neither changes which tickets qualify, only what a qualifying ticket's own columns show), every row carrying a real `ticketTitle`, zero rows with an all-zero Accrue bucket. Confirmed the deferred-fetch split itself (above) is correct end to end: the main route's own response has no `otherRows` key at all, and the separate `/incomplete` route independently returns those same 15 real rows. Under the current 5-minute-variance red/yellow rule, measuring each ticket's real ALL-TIME totals with `offsetHours` folded into END/NO Bill: **24 red**, **4 yellow**, **17 clean** -- 24+4+17 = 45; within the real Complete list specifically, 9 red + 4 yellow, so the new "- 9 Mismatches" heading reading (above) counts only the 9. This is a much more even split than the 42 red/0 yellow/3 clean seen right after the all-time-totals fix landed but before the offsetHours fix -- expected, not a regression: END totals were being massively undercounted until offsetHours was added (see "Offset Hours" above), which made almost every ticket look like it had far less END time than ING; correcting that brought the real split back down to something plausible. Ticket T20260729.0029 itself -- the example that started the all-time-totals investigation -- now shows real, complete, correctly-summed totals regardless of which date range is used to find it: `Accrue--ING` `2.6835`, `Accrue--END` `1.5`, `Accrue--END-No Bill` `1.1834`.

Also confirmed, from testing earlier in this page's build (the underlying bucket-sum/tooltip logic itself is unchanged by any of the later rule changes): a hand-verified ticket's own bucket sums matched an independent raw `TimeEntries` fetch exactly (`other: 0.3333`, tooltip `["Maintenance"]`, once the BillingCodes fix further above was applied); the Resource filter narrows correctly (13 real selectable resources); the Ticket # filter both matches a real ticket exactly and returns `ticketNumberNotFound: true` for a deliberately-bogus one; three different date ranges that each independently qualify the real ticket T20260729.0029 all agree on that ticket's exact same all-time totals rather than three different, date-clipped numbers.

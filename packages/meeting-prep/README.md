# @dashboard/meeting-prep

Dashboard page: search a client, see every reportable chunk of data for them as independent cards ("report components"), tick the ones that actually matter, and preview each one's real content before the meeting. Built for TAMs prepping for a client meeting -- collect only what's relevant, not everything the dashboard happens to track.

- `client.js` -- frontend module: a card grid (one card per component) plus a single always-visible detail panel below it for previewing whichever card was last clicked. Exports `id`, `label`, and `mount(container)`, picked up automatically by the shell.
- `server.js` -- Express router mounted by the shell at `/api/meeting-prep`.

## Why this is a separate page from Check Client, not a section on it

`@dashboard/check-client` already does "search one client, see data from several systems" -- but for a different job: **reconciliation and consolidation** (a fixed set of sections, always shown together, read-only rollups of Orders/Subscriptions/Contracts/etc. for cross-checking one client's whole picture). This page is about **curation** -- pulling in every available piece, then picking a SUBSET to actually present, with the eventual goal (not built yet, see below) of exporting just the picked subset as a PDF or PowerPoint to bring into the meeting. Different job, different UI shape (selectable cards + a picked-subset concept vs. fixed always-all sections), so this is its own page rather than a sixth Check Client section, by request.

## Design: one generic `components` array, not one route per source

`GET /components?client=<term>` returns `{ connected, asOf, siteTerm, components: [...] }` -- every component shares the same envelope (`id`, `source`, `kind`, `title`, `stats`, plus a `kind`-specific payload), regardless of which system it came from. This is deliberate: adding a new source (SaaS Alerts, INKY) means pushing more entries into the same array with a new `kind`, and `client.js` picking up a new `kind` in `statsLine()`/`renderDetail()` -- not a rewrite of the response shape or the card-grid/selection mechanism.

## Data sources: parsed report files, plus two live sources

By request ("let's start with the Datto RMM reports"), then again by request ("I'd like the results of actual reports. See Analytics in DRMM"). Report PDFs (Datto RMM's Report Center -- Executive Summary, Device Health Summary, Device Storage, Hardware Lifecycle, Patch Management Summary -- and, from Dark Web ID, Dark Web Monitoring) get parsed outside this repo and dropped into `data/` as JSON, one file per report per site -- see `data/README.md` for the exact convention, what's in each file, and the current (manual, expected to change) delivery mechanism. `server.js`'s `loadFileReportComponents()` reads whatever's in there on every request and turns each match (against that file's own `site` field, via the dashboard-wide `matchesWildcard()` convention) into a component. Datto RMM's Report Center/Analytics itself still has no REST API at all (confirmed against Datto's own docs), which is exactly why these 6 report kinds have to come from parsing PDFs rather than a live call.

An earlier version of this page also had a live source alongside these -- Datto RMM's own devices/alerts, pulled straight from its REST API with its own 20-minute cache -- removed by request once the file-based report pipeline covered the same ground. **Live Datto RMM devices are back** (by request, "From Datto RMM like you previously did but as widgets like this", pointing at a reference "Core Resources" dashboard screenshot), in a new shape: `server.js`'s `buildDattoLiveDevicesComponent()` reuses Check Client's own Section 5 pattern (`@dashboard/datto-rmm/lib.js`'s `getAllDevices()`, own 20-minute cache, matched against Datto's own `siteName` via `matchesWildcard()`) and renders as KPI tiles, a devices-by-type breakdown, a check-in-freshness bar, and a live-filterable device list -- see "Presentation" below. It's omitted from the response entirely (not shown as an error card) whenever `DATTO_API_KEY` isn't configured, same "quietly not there" convention the rest of this dashboard uses for optional integrations.

**Autotask ticket counts** are a new, deliberately minimal first pass (by request, "ticket counts by Priority, Open and closed in the month... just getting something in there... we will elaborate on this one later"): `server.js`'s `buildAutotaskTicketsComponent()` resolves the search term to one Autotask company (`resolveSingleCompany()`), then counts currently-open tickets by priority plus how many were opened and closed in the current AEST calendar month. See "Autotask ticket counts -- known limitations" below before treating these numbers as final.

## Presentation: widgets first, table data on request

Every one of the 6 file-based report kinds renders as hand-built SVG/CSS widgets (a gauge for Executive Summary's overall score, donut charts for patch/health/lifecycle/dark-web-category breakdowns, coloured capacity bars for storage, a two-bar comparison for this-client-vs-customer-average, a full-width clean/found status banner, coloured tick/cross icons for the pass-fail check grids) sitting above a collapsed `<details>` holding the same data as a plain table, by request ("reporting like this at the beginning of the report with the ability to include the table data where required"). No chart library was added for this -- `client.js`'s `gaugeSvg()`/`donutSvg()`/`barWidget()`/`checkIconSvg()`/`compareBarsWidget()`/`statusBanner()` are all plain inline SVG/CSS, since the shapes needed didn't justify a new dependency in a codebase that doesn't use one anywhere else. Worth revisiting if this ever grows into trend-over-time charts (a client's score across several report runs) once report history actually accumulates -- multi-series line charts with legends/tooltips is where hand-rolled SVG stops being the pragmatic choice.

Different report kinds deliberately use different widgets for their own data ("it's ok to use different ones in different places") -- there's no single shared "report widget" component, each of the 6 `*WidgetsHtml()` functions in `client.js` picks whatever actually fits that report's own numbers. Dark Web Monitoring in particular leads with `statusBanner()` rather than a widget-grid item, since "clean month, nothing found" is a genuinely good and common outcome for this report and deserves to read as a clear headline rather than an empty donut buried among the others.

The two live components add three more widget shapes, built to match a reference "Core Resources" dashboard screenshot Amber shared: `kpiTileRow()` (a row of stat tiles, optionally colour-tiered good/warn/bad -- used by both live-Datto and Autotask-tickets), `deviceTypeBarWidget()` (reuses the existing bar-row/swatch styling rather than a new chart), and `checkinFreshnessWidget()` (one bar split into coloured segments by proportion, a shape none of the file-based reports needed). Live Datto devices also get `deviceListTableHtml()` -- a genuinely live-filterable table (`wireDeviceFilters()` wires a plain substring match, against hostname + last user together, into the table on render), the first widget on this page with its own JS behaviour rather than a static string, since a real device list is long enough to be worth narrowing down. There's no collapsed "show full table data" underneath either live component -- the KPI tiles + filterable table already are the whole picture, so a second copy of the same numbers would just be clutter.

An earlier version of this page rendered exact, pixel-unaltered crops of the source PDF instead (`data/images/`, generated by the same parser, served at `/api/meeting-prep/images/`) -- proven to work and genuinely pixel-identical to Datto's own report, but superseded once the widget version covered the same need with real interactive data behind it, by request. The server-side crop generation and the `/images` static route are untouched (`loadReportImages()` in `server.js`, still returned as each component's `images` field) in case a future PDF/PowerPoint export wants exact source images again -- they're just not rendered on this page any more.

**Client / Site search** is one field, matched via the dashboard-wide `matchesWildcard()` convention (`@dashboard/autotask-client`) against each file-based report's own `site` field (see `data/README.md`) -- not a per-source field the way Check Client splits Autotask/Ingram/Datto. That works as long as every source's `site` value actually agrees on what to call a given client; Dark Web ID's own report text doesn't necessarily match Datto's own `siteName` convention out of the box, so this needs a manual check each time a new non-Datto source is added for a client (see the gotcha in `data/README.md`) rather than being something to assume is fine. The same one search term also drives live Datto site matching (`matchesWildcard()` against Datto's own `siteName`, same convention) and Autotask company resolution (`resolveSingleCompany()`, which expects something that resolves to exactly one real company name/wildcard) -- three different naming systems assumed to line up well enough off one box, same trade-off Check Client's own "Datto Site" field exists specifically to avoid (see that page's own comment on why Datto's site names get their own editable field there). Worth revisiting here too if a client's names genuinely diverge across systems.

### Autotask ticket counts -- known limitations

Flagged explicitly rather than presented as settled, since this was built as a deliberately minimal first pass:

- **"Open"** is "no completion date yet" (`notExist completedDate`), the same definition `@dashboard/tickets-dashboard` already uses -- which means a status-20 "Billing - Contract" ticket sitting in billing still counts as open (Autotask never sets a `completedDate` on those), same documented caveat that page carries.
- **"Opened in \<month\>" and "Closed in \<month\>"** are ticket-volume-in/-out figures -- every non-monitoring-alert ticket created, or closed, in the current AEST calendar month, regardless of whether an "opened" one has since been closed. "Closed" reuses `@dashboard/completed-tickets`'s own confirmed real definition (status 5 by `completedDate`, UNIONed with status 20 by `resolvedDateTime`); "Opened" (`createDate` in the month) isn't independently confirmed against any existing page, since nothing else on this dashboard counts tickets opened-in-a-month -- worth checking against Autotask's own UI count before relying on it.
- **No date-range picker** -- always "the current AEST month," unlike Completed Tickets' own From/To selector. Deliberately left out for this first pass.
- **Company resolution can come back `ambiguous` or `not-found`** -- surfaced as a plain message in the card rather than guessed at, same "don't guess, ask for a narrower search" reasoning `resolveSingleCompany()` was built around.

## Recommendations summary

"Generate Recommendations Summary" (top of the page, next to the title, shown once a search has returned at least one component) cross-references whatever's currently loaded and surfaces what's worth fixing, finding out more about, or bringing up before the client meeting -- by request. Deliberately rules-based, not an LLM call (there's no AI backend wired into this dashboard): `client.js`'s `buildRecommendationsSummary()` runs a fixed set of checks (patch policy gaps, disk space, the weakest Executive Summary category cross-referenced against which devices are actually failing it, hardware due for replacement cross-referenced against which of those devices are already causing trouble elsewhere, warranty data that isn't populated, dark web monitoring scope, whether the loaded reports even agree with each other on a device count or a report date, and so on), each one skipping itself gracefully when its report kind isn't loaded for this client. It's explicitly framed in its own output as a starting point, not a replacement for actually reading the reports -- the underlying JSON doesn't carry everything a human reading the PDF would notice (e.g. it can flag that Software Management is the weakest score and list which devices are failing the check, but can't say *which software* is the problem, since that's not in the parsed data at all).

Findings are grouped by urgency (fix before you present / find out before you present / worth mentioning in the meeting / good news to lead with) rather than by which report they came from, since that's the axis that actually matters when you're deciding what to do with an hour before a client meeting, not which system happened to produce the underlying number.

## Selecting components

Each card has its own checkbox ("include in the meeting pack") -- clicking the card body (not the checkbox) instead opens/closes that component's full content in the detail panel below the grid, so you can review before deciding whether to tick it. Both are independent: ticking a box doesn't open the preview, and previewing a card doesn't tick it. Selections persist in memory across a remount (navigating away and back) but are cleared the moment a genuinely different client is searched -- a pick is scoped to whoever you just searched for.

**Tick All / Invert Ticks / Untick All** -- three small buttons above the card grid, by request, for bulk-changing which cards are ticked without clicking each one. "Invert Ticks" is this page's own name for what's more commonly called "Invert Selection" elsewhere (Photoshop, Windows Explorer's own Edit menu, most file-manager/list UIs) -- named "Ticks" here purely to match this page's own existing vocabulary (every card already calls this a "tick"), not because the operation itself differs. All three act on `selectedIds` directly, same Set every individual checkbox already mutates, then re-render the grid from that new state rather than patching checkboxes in place -- same "rebuild from state" approach `reorderComponent()` already uses for its own bulk change. Hidden until a search has actually returned components, same as the Recommendations Summary button next to it.

**Drag to reorder** -- by request, every report card can be dragged and dropped onto another to change its position in the grid; plain HTML5 drag-and-drop, no library. `client.js`'s `componentOrder` (a plain array of component ids) tracks the current order; `orderedComponents()` reconciles it against whatever the API actually returned on each render (a component that's disappeared since -- e.g. Datto RMM not configured this run -- is dropped from the order, and one that's newly appeared is appended at the end, so a manually-dragged order degrades gracefully rather than breaking). Same in-memory, per-search scope as the selections above: reordering persists across a remount but resets to the server's own default order (`REPORT_ORDER`, then the two live components) the moment you search a different client -- not saved to a database or localStorage, so it doesn't survive a full page reload either. The "Selected Overview" tile is deliberately NOT draggable and always stays first -- it's a pinned utility tile, not a report to reorder, same reasoning it already has no checkbox of its own. Native HTML5 drag-and-drop has no touch-screen support, so this is a mouse/trackpad-only interaction for now -- worth revisiting with a pointer-based reorder library if this page is ever used on a tablet.

**"Selected Overview"** is always the first tile in the grid, by request ("as the first selection, a tile which shows the widgets from all sections with ticks on"). It isn't one of `data.components` -- no checkbox of its own, doesn't count toward "N components found" -- it's a live preview OF whatever you've ticked, not a component to tick itself. Clicking it shows every currently-ticked component's own widgets (just the widgets, not the collapsed table data -- the individual card is still there for that) stacked in the same fixed order they appear in the grid. Its tick count and, if it's the one currently open, its own preview update immediately as you tick more boxes, without needing to re-open it. Nothing ticked yet is a normal starting state, not an error -- it just asks you to tick something.

## Not yet built

- **Confirming the Datto `deviceType` field against a real payload** -- `@dashboard/datto-rmm/lib.js`'s `mapDeviceSummary()` now reads `device.deviceType?.category`, added purely additively for this page's own "Devices by type" breakdown and TYPE column. Unlike every other field in that mapping (each checked against a real raw device dump, per that file's own header comment), this one is based on Datto's public API docs only, not a live payload from this account -- flagged both in code comments and in the UI itself (a caveat line under the widget) until someone checks it against a real device and confirms or fixes the category labels.
- **Elaborating the Autotask ticket counts** -- explicitly a first pass, by request ("just getting something in there... we will elaborate on this one later"). See "Autotask ticket counts -- known limitations" above for exactly what's provisional (the "opened in month" definition in particular) versus already reused from a confirmed source elsewhere on this dashboard.
- **Automated pickup of report files** -- today, getting a report PDF into `data/` (parsing it, naming it right, putting it in this repo) is a manual step done outside this page entirely. The plan is a SharePoint drop folder plus a scheduled job that detects, parses and writes new reports on its own; see `data/README.md`. Both parsers (Datto RMM's 5 report types, and now Dark Web ID's monthly report) are proven against real samples but neither is yet checked into this repo or automated.
- **PDF/PowerPoint export of the selected components** -- the actual end goal ("create a PDF or PowerPoint from that"), deliberately deferred. Ticking a box currently only highlights the card and updates the "N selected" count in the summary line; nothing consumes that selection yet. Building this next means picking an export path (a server-side PDF/PPTX generator over the same `components` data, most likely) once the picking/preview UX above has been used for real and any adjustments to it are in.
- **Other sources** -- SaaS Alerts already has its own client-name-filterable alert feed (`@dashboard/saasalerts-alerts`) and is the natural next addition, following the exact same "push more entries into `components`" pattern this page was built around. Dark web monitoring is now wired in (Dark Web ID, see `data/README.md`); INKY still has no dashboard integration at all.
- **Layout alternative** -- a list-down-the-side-with-content-to-the-right layout was considered as well as the card grid; the card grid was built first since it reuses Datto RMM's own existing `.datto-card-grid`/`.datto-card` CSS almost as-is. Worth revisiting once there's real usage to react to.

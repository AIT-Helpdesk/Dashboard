# @dashboard/tc-elite-rollout

Dashboard page: tracks TC Elite product/service rollout status per client -- a colour-coded grid (client rows x product/service columns), staff-editable directly here, with every change attributed to a real signed-in user and timestamped. Replaces a manually-maintained Excel workbook that had no audit trail and no quick "what's still outstanding" view.

- `client.js` -- frontend module. Exports `id`, `label`, and `mount(container)`, picked up automatically by the shell.
- `server.js` -- Express router mounted by the shell at `/api/tc-elite-rollout`.
- `db.js` -- schema + the shared write helpers (`recordAudit`, `recomputeRollup`, `seedNewClient`/`seedNewColumn`/`seedNewStage`). Everything that touches the database goes through this file, not raw SQL scattered through `server.js`.
- `scripts/import-from-xlsx.js` -- the one-time migration from the original spreadsheet. Already run once against the real file; kept in the repo for transparency/auditability, not meant to run again (see its own header comment).

## The first page here with its own persistent, writable data

Every other page on this dashboard is a thin read view over an external system (Autotask, Strety, Ingram, Teams), with at most a short in-memory cache. This page needed a real datastore -- clients, the rollout columns tracked for each, per-cell status, and a full audit trail.

Uses node's own built-in **`node:sqlite`** (`DatabaseSync`), not a third-party package -- confirmed working (`CREATE TABLE`/`INSERT`/`SELECT` round trip) before committing to it. Needs **Node >=22.5**; this repo's root `engines` field currently only requires >=20, so if this is ever deployed to a box running an older Node, that's the first thing to check (`node --version`). Zero new runtime dependencies this way, and no native-binary-on-Windows risk the way `better-sqlite3` would have carried.

`data.db` lives in this package's own folder, gitignored (along with its `-shm`/`-wal` WAL sidecar files) -- same "runtime state, not source" convention as `packages/shell/nav-layout.json` and the Strety token files. `PRAGMA journal_mode = WAL` is set on startup so multiple staff editing around the same time don't block each other the way the default rollback journal would.

## Schema -- structure vs. current value vs. history, as three separate concerns

- **`clients`** / **`columns`** / **`stages`** -- the STRUCTURE: which clients exist, which rollout items are tracked, and (for `kind='compound'` columns only) which stages make up that item's own detail sheet. A stage's `type` is `'status'` (one of the four states, feeds the rollup) or `'text'` (a free-text field like AutoElevate's "WHO"/"Domain" -- purely informational, never part of the rollup calculation).
- **`cell_status`** / **`stage_status`** -- the CURRENT value for each (client, column) / (client, stage) pair. For a `kind='simple'` column, `cell_status` is directly editable (`PATCH /cells/:clientId/:columnId`). For a `kind='compound'` column, `cell_status` is the **auto-computed rollup** from that client's `stage_status` rows -- `recomputeRollup()` in `db.js` is the only thing that ever writes it; there is no direct-edit path for a compound column's own master cell.
- **`audit_log`** -- append-only history. Every `cell_status`/`stage_status` write (and client/column/stage creation) writes a row here first. This is the real reason the page exists rather than staying a spreadsheet: it powers the "Started by `<name>` on `<date>`" hover tooltip, and there's deliberately no separate "Commenced"/"Completed" column on `clients` -- those are meant to be derived from this table on demand (first non-`not_done` change for a client; when a client's last outstanding item became `done`/`na`) rather than duplicated as their own maintained fields.

## The six states, and the rollup rule

`not_done` (red, ✗) / `started` (amber, ▶) / `done` (green, ✓) / `na` (light green, "N/A") / `cancelled` (light green, ⛔) / `issue` (light purple, ⚠️). `started` is deliberately kept distinct from `not_done` -- by request, the person who sets a cell to Started is a real clue to who's actually working on it, which is exactly what the audit-log-backed hover tooltip surfaces. `na`, `cancelled`, and `issue` all accept an optional short comment/reason (`STATUSES_WITH_COMMENT` in both `server.js` and `client.js`) -- na's "why doesn't this apply", cancelled's "why was this cancelled", issue's "what's the issue".

`na` and `cancelled` share the same light-green tint (`cancelled` means "we decided not to do this for this client" rather than "not applicable to begin with", but reads the same at a glance) and both count as **resolved** -- see the default-view section below. `issue` is the opposite kind of special case: it's styled in the same visual tier as not_done/started/done (a stronger 18% colour tint, not na/cancelled's lighter 13%) and deliberately does **not** count as resolved -- a flagged issue needs to stay visible in the default view until someone actually fixes it, not get hidden away by the "what's waiting to be done" filter.

`cancelled` and `issue` were both added after the initial build (see "Adding the Cancelled status" and "Adding the Issue status" below).

A compound column's `cell_status` is computed from its **`status`-type** stages only (`text`-type stages never participate). `na` and `cancelled` stages are both treated as "ignorable" -- they don't count toward the rollup unless *every* relevant stage shares the same ignorable status, in which case the rollup reflects that specific status rather than falling back to a generic default. `issue` is never ignorable -- it takes priority over everything except na/cancelled:

- zero status-type stages at all -> `na`
- ignoring any `na`/`cancelled` stages, if none remain: all `cancelled` -> `cancelled`; otherwise -> `na`
- ignoring any `na`/`cancelled` stages, if ANY of the rest is `issue` -> `issue` (even just one problem stage surfaces at the master-grid level, rather than getting diluted into a generic `started` reading)
- ignoring any `na`/`cancelled` stages, all the rest `done` -> `done`
- none of the rest `started`/`done` -> `not_done`
- otherwise -> `started`

Recomputed synchronously by `recomputeRollup()` (`computeRollupStatus()` is the pure function) after every `stage_status` write -- not a background job, not eventually-consistent. Verified against real imported data (see below) that this produces the same answer a human scanning the sub-sheet would.

## The "what's waiting to be done" default view

A cell is **resolved** if `done`, `na`, or `cancelled` (nothing left to do -- `RESOLVED_STATUSES` in `server.js`); **outstanding** otherwise (`not_done`/`started`/`issue`). The default view (`GET /` with no `?all=true`) hides columns where every client's cell is resolved, then -- among only the columns still visible after that -- hides client rows where every one of *those* cells is resolved too. A client fully done/na/cancelled except for one column everyone else has also already resolved doesn't clutter the default view; a client with even one `issue` cell stays visible everywhere that matters. `?all=true` (the "Show All" toggle in `client.js`) bypasses this entirely, same "Show Completed" convention Service Calls' own toggle uses.

## New clients / new columns / new stages all seed the same way

New client rows mark every existing column Not Done, by request. New columns seed Not Done across every existing client; new stages (added to an already-existing compound column) do the same, then recompute every client's rollup for that column -- a freshly added stage can change what "all done" means for a client that was previously fully done on it. All three seeding paths (`seedNewClient`/`seedNewColumn`/`seedNewStage` in `db.js`) go through the same `computeRollupStatus()`/`recomputeRollup()` rather than hardcoding `not_done` for compound columns directly -- confirmed necessary: a compound column with zero stages should correctly seed to `na` (nothing to track yet), which only happens if seeding genuinely runs the real rollup rule instead of assuming the answer.

**Real bug found and fixed while testing this**: the first version only seeded `stage_status` rows for `status`-type stages, on the assumption a `text`-type stage "starts blank" and doesn't need one. It does -- `PATCH /stages/:clientId/:stageId` is a plain `UPDATE`, not an upsert, so a text stage with no seeded row returned a confusing 404 the first time anyone tried to fill it in. Every stage (status or text) now always gets a row the moment both it and the client exist; `status` is `not_done` for status-type, `NULL` for text-type.

**Client lists are sorted case-insensitively.** Both `GET /` (master grid) and `GET /columns/:id/detail` originally sorted with `ORDER BY name`, SQLite's default case-SENSITIVE (`BINARY`) collation -- which sorts every uppercase letter before every lowercase one, so a client starting with a lowercase letter (e.g. "iCar Service") sorted after every single uppercase-first name instead of alphabetically among them. Fixed with `ORDER BY name COLLATE NOCASE` in both queries.

## Bulk row-set (whole row, one status/comment in one go)

Each row (master grid or a compound column's detail sheet) has a bulk-set control that applies one status (+ comment where the status accepts one) to every cell/stage in that row at once -- `PATCH /clients/:clientId/bulk-cells` (master) and `PATCH /columns/:columnId/clients/:clientId/bulk-stages` (detail sheet), both in `server.js`, backed by `bulkSetCells()`/`bulkSetStages()` in `db.js`. Each cell/stage touched gets its own `audit_log` row, same as an individual edit -- a bulk-set is not a special audit entity, just many ordinary writes done together.

On the **master grid only**, after a bulk-set succeeds `client.js` asks (via `confirm()`) whether to also cascade the same status/comment to every compound column's sub-sheet for that client (AutoElevate, EasyDMARC, etc.) -- confirming loops over every `kind='compound'` column and calls the same bulk-stages endpoint for each. Declining leaves the sub-sheets untouched (their own rollup stays whatever it already was, which may then disagree with the master cell until someone visits the detail sheet directly -- expected, since the master cell for a compound column is otherwise always the computed rollup).

## Adding the Cancelled status

Added after the initial build, by request: a 5th status, `cancelled` (⛔), styled identically to `na` (light green) but recorded as its own value, with an optional comment. Required a real schema migration since SQLite can't `ALTER TABLE` a `CHECK` constraint directly -- `migrateAddCancelledStatus()` in `db.js` uses the standard create-new-table-with-the-wider-constraint -> `INSERT ... SELECT *` -> `DROP TABLE` -> `RENAME TO` pattern, wrapped in a transaction, run automatically on module load and guarded (checks `sqlite_master.sql` for the literal `'cancelled'` substring) so it's a no-op on every load after the first. No data was lost or rewritten by this migration beyond the constraint itself -- every existing `cell_status`/`stage_status` row keeps its original status, timestamp, and audit history untouched.

## Adding the Issue status

Added after Cancelled, by request: a 6th status, `issue` (light purple, ⚠️), for "this specifically has a known problem" as distinct from the ordinary not_done/started states. Same migration pattern as Cancelled (`migrateAddIssueStatus()` in `db.js`, guarded on the `'issue'` substring instead). Unlike na/cancelled, `issue` is deliberately never ignorable in the rollup and never counts as resolved in the default-view filter -- see "The six states" above for the reasoning and the exact rollup precedence.

**A real data-integrity bug found (and fixed) while building this feature, worth recording**: an earlier verification script for the separate "Add Stage" feature added a temporary stage directly to the real `BSE - TC Essentials` column to test against, then cleaned up afterward with raw `DELETE FROM stages/stage_status/audit_log` statements instead of calling the real `deleteStage()` helper in `db.js`. `deleteStage()` doesn't just delete rows -- callers are expected to also call `recomputeRollup()` for every affected client afterward, since removing a stage changes what "done" means for that column. The raw-SQL cleanup skipped that, leaving every client's `BSE - TC Essentials` master cell stuck at whatever it was while the temporary stage still existed (mostly `started`), even though the real underlying stages were genuinely `done`. This surfaced as a real user-visible symptom: the column's "Show Detail" section stopped being hidden by the default filter even though every row was actually complete. Fixed with a one-off repair script that called the real `recomputeRollup()` for every client on that column (attributed to a `system@ambientit.internal` actor in the audit log, not a real staff member, so the trail stays honest about what was a real edit vs. a data-integrity fix) -- confirmed correct afterward by comparing every compound column's stored rollup against a fresh `computeRollupStatus()` calculation from the real stage data (zero mismatches). **The lesson**: any verification script that creates structural data (a stage, a column) against a REAL existing entity, not a disposable throwaway client, must clean up via the real `db.js`/API helpers, never raw SQL -- this is why later verification scripts in this build (e.g. for Issue) only ever exercise a throwaway client against already-existing real structure, and delete that client via the real `DELETE /clients/:id` endpoint.

## Add Column / Add Stage are restricted to one person

Adding a whole new column, or a new stage to an existing compound column's detail sheet, changes what every client/staff member sees -- by request, both are restricted to a single person (`amber@ambientit.com.au`) rather than every signed-in user. `COLUMN_ADMIN_EMAIL`/`isColumnAdmin()` in `server.js` is the real enforcement -- both `POST /columns` and `POST /columns/:columnId/stages` return `403` for anyone else. `client.js` mirrors the same check (fetched once from `/api/me` on mount) purely for UX -- everyone still sees and can click the "Add Column"/"Add Stage" buttons, they just get an immediate `alert('See Amber to authorise this function.')` instead of the form opening, rather than a wasted round trip to the server. This is a one-person allowlist, not a role/permissions system -- if that ever needs to generalise, `isColumnAdmin()` is the one place to change.

## Every cell's hover tooltip, and the full change-history window

Every `.tcr-cell` (not just `started` ones) shows a hover tooltip with the cell's status/reason plus **who last changed it and when** -- `showCellTooltip()` in `client.js` shows the synchronous status/reason content immediately, then fills in the who/when line once the on-hover history fetch resolves (guarded against a stale response landing after the mouse has already moved to a different cell). The tooltip itself is hoverable (not the usual `pointer-events: none`), with a short grace period before it hides (`scheduleHideTooltip`/`cancelHideTooltip`), specifically so the cursor can reach its "View full history" link/button without the tooltip disappearing first.

Clicking that link -- or clicking a **non-editable** cell directly (only ever a compound column's own auto-computed rollup on the master grid, which otherwise has no click action at all) -- opens `openHistoryModal()`: a simple overlay + panel listing every audit entry for that one cell/stage, most recent first. Editable cells keep their existing click = open-the-status-editor behaviour unchanged; the history window is reached via the tooltip's link for those, so there's no conflict between "click to edit" and "click to see history."

`GET /cells/:clientId/:columnId/history` and `GET /stages/:clientId/:stageId/history` back both the tooltip (uses just the first/most-recent entry) and the modal (uses the whole list), limited to 200 entries -- generous enough to be "the full history" for any real cell in practice, without an unbounded query against a table that's genuinely append-only forever. Never fetched eagerly for the whole grid up front (which could be dozens of clients x a dozen-plus columns), only on demand per cell.

## The import: real column mapping, confirmed against the actual spreadsheet

`scripts/import-from-xlsx.js` migrated the original `TC-Elite Rollout Tracking - Claude.xlsx`. Nothing here is guessed -- every row range and column index below was confirmed by dumping the raw sheet data and reading it, not assumed from the header labels alone.

**Master sheet ("TC ELITE EXTRAS")**, columns B/C/K/L become plain client metadata (`active_contract`/`name`/`comment`/`contract_signed`), not grid cells. Columns A, D-J, M, AB-AF are skipped entirely (I/"Commenced" and J/"Complete" are meant to be derived from the audit log instead, per the reasoning above, not stored directly). Columns N-AA plus AG/AH are the real tracked grid: nine simple columns (Autotask Classification, Autotask/T&M Contract, Entra ID Backup, TPP Category, Huntress, Bullphish, Schedule Site Visits, Sentinel PC, Network Glue), plus two compound columns whose stages live **inline on this same sheet**, not a separate one (BSE - TC Essentials: SaaS/Endpoint; RMM Policies: In RMM/Policies/Reporting).

**Two compound columns have a real linked detail sheet**: EasyDMARC (own sheet "EasyDMarc Specifics") and AutoElevate (own sheet "Autoelevate Specifics"). Their master-sheet columns (X and Y) were **not read at all** during import -- those held the old manually-kept rollup, which this system now computes itself from the real per-stage data on each detail sheet (`recomputeRollup()`, run for every client against these two columns once all stages are imported). Each detail sheet also has its own text-type metadata fields folded in as `type='text'` stages (WHO, Comment, plus Domain for EasyDMARC and Commenced/"Anything Else?" for AutoElevate) -- informational, never part of the rollup.

**Row ranges are hard-coded to the confirmed real boundaries**, not "read until the row is blank" -- this script is a one-time migration against one specific file, not a general-purpose importer, and reading-until-blank would have been actively wrong here: the master sheet has a `COUNT`/`SUM` footer two rows after the real data (`"25"`/`"444"` would otherwise import as two fake clients), and Autoelevate Specifics has a notes/legend section starting several blank rows after its real data ("Instructions:", "Thoughts:", "Elevation Mode: / Stage #1: / Optimised: / Stage #2: Live Mode" -- three more fake clients, caught the same way). Both were caught by running the import, inspecting the actual resulting client list, and finding names that were obviously not real clients.

**Two genuine inconsistencies in the source data itself**, found the same way: the Autoelevate Specifics sheet spells one client "Queensland Greyound Racing Club" (missing the "h") where the master sheet and EasyDMarc Specifics both agree on "Queensland Greyhound Racing Club", and has another as bare "PacGold" where the other two sheets agree on "PacGold #2". `normalizeClientName()` in the import script corrects both (2-of-3 sheets agreeing on the real spelling is the basis for treating them as the same client, not two separate ones) -- worth knowing this was a judgment call on real, messy data, not a certainty.

**Value mapping**, applied to every simple-column and status-stage cell: `YES` -> `done`, `NO` -> `not_done`, `Started` -> `started`, everything else (`Skip`, `Too Old`, `Too Small`, `Too Diverse`, `SaaS Only`, `Email Only`, `No DNS Access`, `Maybe`, blank) -> `na`, with the original text kept as the reason (blank stays `na` with no reason -- nothing was ever recorded there). `Maybe` landing on `na` in particular is a judgment call, not a certainty -- easy to correct for real via the UI post-import if wrong, nothing about this mapping is destructive.

**Verified against real data**: spot-checked two clients' full stage-by-stage values (Blake Sign & Co / AutoElevate, Brisbane North Chamber of Commerce / EasyDMARC) directly against the raw spreadsheet cell-by-cell -- exact match on every stage and reason, and the computed rollups (`started` for a genuinely mixed set of stages, `done` for a single relevant `done` stage among several `na` ones) matched what a human reading the sheet would conclude.

Final counts: 27 real clients, 13 columns (9 simple, 4 compound).
